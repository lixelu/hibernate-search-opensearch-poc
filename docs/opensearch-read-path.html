OpenSearch on the read path

Adopt OpenSearch as a query accelerator, not a second source of truth. It decides which rows and in what order; MySQL still returns what is in them. Six decisions, one reversible switch, and a reference implementation that measures every claim below.

The six decisions

Everything else in this document follows from these. Each is reversible by configuration, and each is implemented in the reference service.

D1 Search returns ids and sort order; MySQL hydrates the payload by primary key storing the full API response in the index
D2 A transactional outbox carrying only the aggregate id dual writes from the service, or CDC on day one
D3 Every document carries the aggregate's monotonic version as an external document version trusting arrival order
D4 Reads and writes address aliases; a rebuild is an alias move mutating a live index's mapping
D5 One SearchPort, two adapters, a router with shadow mode and automatic fallback a feature flag wrapped around a second code path

02

Why index tuning plateaued

The GET endpoints are slow not because MySQL is slow, but because the work the query asks for grows with the result set rather than with the page.

  1. Filters live in five tables. Vendor attributes, category path, tags, EAV attributes and regional stock each need a join or an EXISTS fan-out. No composite index spans tables, so the optimiser picks one driving index and filters the rest row by row.
  2. Sort keys are derived. "Cheapest variant price" is a MIN() over a child table. Sorting by it means computing it for every candidate row before discarding all but 20.
  3. The combination is caller-controlled. Ten optional filters and five sort fields make hundreds of shapes. You cannot carry hundreds of useful composite indexes, and each one taxes every write.
  4. The count costs as much as the page. LIMIT 20 bounds rows returned, not rows examined — and the pagination COUNT(*) examines them all again.

Indexes reduce the constant factor. They cannot change the fact that the filter/sort combination is known only at request time and spans tables.

What an inverted index changes: it pre-computes at write time exactly what the query needs at read time — one flat document per aggregate, postings lists per filter term, doc-values columns per sort field. Filtering becomes an intersection of sorted id lists; sorting becomes a scan of one column. The join, the fan-out and the correlated sub-query are paid once, off the request path.

That is also its whole limitation: only query shapes you anticipated at index time get the speedup, and the data is exactly as fresh as your ingestion pipeline.

04

Architecture

Two paths that meet only at the database. A write never touches OpenSearch; a read never blocks on it.

D1 — the index accelerates the query; MySQL still owns the payload

The search returns ids and sort values only — _source fetching is switched off entirely. The page is then hydrated from MySQL with a batched primary-key lookup.

Five milliseconds is the entire cost of this choice, against a 200–1500 ms saving. It also makes both adapters return the same type — ordered ids plus a total — which is what reduces shadow comparison and instant fallback to a few lines rather than a project.

The row is (aggregate_type, aggregate_id, occurred_at) plus claim fields — about 70 bytes, no payload. That buys three properties:

  • Coalescing. Twenty writes to one product in a poll window produce twenty rows but one aggregate load and one indexed document. Bulk imports and price feeds cost the index almost nothing extra.
  • Idempotent replay. The relay always reads current state, so redelivery is a no-op or a newer write. There is no stale payload to apply.
  • Deletes come free. An id the loader cannot find is a delete — no tombstone events, no special case in the write path.

The write path's entire footprint is two lines, kept explicit rather than hidden in an entity listener, so a reviewer can see on any new write method whether the index will hear about it:

// inside the transaction that already exists
product.bumpVersion();
outbox.productChanged(product.getId());

Recording is @Transactional(propagation = MANDATORY): calling it outside a transaction fails loudly rather than quietly reintroducing the dual-write problem. The relay claims work with SELECT … FOR UPDATE SKIP LOCKED, so every instance can poll the same table — no leader election, no ShedLock.

Claim, then delete — never delete, then index

The cycle is claim → load → index → delete. That is at-least-once across a crash, and D3 makes at-least-once harmless. Deleting first would be at-most-once: silent data loss in the index on any crash.

06

Versioning and aliases

D3. aggregate_version is a monotonic counter bumped by every write to the aggregate — including writes that only touch a child table, such as a variant reprice. It is sent as the external document version with external_gte, so the cluster itself refuses to install an older document. One flag handles four hazards:

  • Two relay workers on the same aggregate cannot interleave into a stale result.
  • Redelivery after a crash is a no-op.
  • A full backfill can run against a live index — an old snapshot row loses to the live version.
  • The relay may read from a lagging replica without overwriting a fresher document.

The price: a 409 in the bulk response is a normal outcome, counted as stale, not an error. Code that treats it as a failure will retry forever.

D4. Nothing addresses a concrete index. Reads go through products_read, writes through products_write; physical indices are products-v1, products-v2, … A rebuild — measured at 14.7 s for 101,400 documents — is:

1. create products-v(N+1) from the mapping resource
2. move the WRITE alias to it        — live changes land in the new index
3. backfill by keyset over the PK       — old rows lose to live ones on version
4. refresh, then move the READ alias  — readers cut over atomically
5. drop products-vN once you are happy

Step 3 is safe next to step 2 only because of external versioning. The one caveat: between steps 2 and 4 the old index stops receiving updates, so aborting mid-rebuild leaves it behind — recovery is to move the write alias back and replay the window.

Risks — and one finding

Found while building the reference implementation

Descending sort on a scaled_float field can silently return non-maximal documents

Ordering diverged between the two engines on a deep page. The divergence was in OpenSearch: a descending sort returns documents that are not the maximum, while a max aggregation on the same field, in the same query, reports the true maximum.

GET products/_search {"sort":[{"ratingAvg":"desc"}], "size":1}    → 3.12
GET products/_search {"aggs":{"m":{"max":{"field":"ratingAvg"}}}}  → 5.0

docvalue_fields confirms the true-maximum document exists, matches the filter, holds doc-value 5.0 — and is simply not returned first. Reproduced on OpenSearch 2.19.6 and 3.8.0, single shard, force-merged to one segment, with and without concurrent segment search. It is data-dependent: sometimes off by one tick (199.97 for 200.00), sometimes badly wrong. Adding a range filter masks it, which is why it survives casual testing.

Field typeAscending sortDescending sort
scaled_floatcorrectWRONG
float, double, half_float, long, integercorrectcorrect

Mitigations, already applied: money is stored as long minor units and ratings as float — never scaled_float on a field you sort by; the OpenSearch version is pinned and the parity check re-runs on every upgrade; and shadow mode is treated as mandatory, because comparing id lists is what surfaced this. No amount of code review would have.

The other risks

  • Pagination. from + size is capped at 10,000; past that callers move to search_after, for which the tiebreaker sort is already in place.
  • Totals are a lower bound past 10,000 hits, and the response says so. This is the one visible contract difference in the whole migration — confirm it with API consumers.
  • No read-your-writes. Steady-state lag is sub-second, but it is not zero. Read the entity by primary key after a write (that path never touches OpenSearch), or insert it client-side. Never reach for refresh=true — it destroys indexing throughput.
  • Hard deletes carry no version, so a delete racing a re-create of the same id could resurrect a document. If ids are reused, switch to a soft-delete flag and deletes become ordinary versioned updates.
  • Data classification. Only filter and sort keys reach the cluster today, so no PII does. Keep that deliberate: adding a customer name to the index is a data-protection decision, not a mapping decision.

What must not move: point lookups by primary key, anything transactional, any read a write decision depends on, ad-hoc reporting whose filters are not known in advance, and exact counts on very large result sets.

Rollout

Six phases, each with an exit criterion. The order is the point: nothing customer-facing changes until the two engines have agreed for a week on real traffic.

0 FoundationsCluster provisioned, mapping reviewed, outbox and relay deployed with the engine still set to MySQL ExitBacklog drains; lag p99 under 5 s at production write load
1 BackfillFull reindex; nightly reconciliation switched on ExitZero missing, zero stale for a week
2 ShadowMySQL answers; OpenSearch runs alongside and divergences are counted ExitMismatch rate flat at zero for a week across real query shapes, not synthetic ones
3 CanaryOpenSearch answers for a small traffic share, via the per-request override Exitp95 improves, error rate flat, fallback counter at ~0
4 DefaultFlip the deployment default; keep the MySQL adapter and the fallback ExitTwo weeks stable
5 ExtendThe next endpoint family; consider CDC only once the outbox is straining Exit—

Do not delete the MySQL adapter

It is the fallback, the shadow reference, and the thing that makes rollback a configuration change rather than a deploy.

Effort. The reference implementation is ~3,500 lines of Java, of which ~1,100 are the integration itself — outbox, relay, indexer, projection, adapter, translator, index admin. The rest is the demo domain, the MySQL baseline and the benchmark harness: code you already have or do not need. Budget 2–4 weeks for one engineer to take the first endpoint family to production, plus cluster provisioning. Subsequent endpoints are days — the pipeline is shared, and only the projection and the translator grow.

12

Open questions

  1. Volume and shape. Row counts and average document size for the real aggregate, to turn the sizing formula into a cluster.
  2. Tenancy. If the data is multi-tenant: a filter plus routing key by default; one index per tenant only for very few, very large tenants.
  3. Which endpoints first, ranked by p95 × call volume. The benchmark harness can rank them against real query shapes.
  4. Are exact totals contractual on any endpoint?
  5. Write burst profile — peak writes per second and the largest bulk import, to size the relay batch and interval.
  6. Is there a read replica the relay's aggregate loads can use?

Every figure on this page was measured on the accompanying reference implementation — a runnable Spring Boot service with MySQL and OpenSearch in Docker Compose, 3 unit tests and 4 Testcontainers integration tests covering outbox delivery, child-table writes, deletes and stale-version rejection.

Absolute latencies are laptop numbers; the ratios and the shapes are what transfer.
