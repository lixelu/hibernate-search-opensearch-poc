Which class does what

A write touches three stores in one transaction and never speaks to OpenSearch. A read picks one of three engines, gets back ids, and hydrates the page from MySQL. One loader class sits on both paths — which is the part worth knowing.

Write path

One transaction, three stores

Everything below happens inside the transaction the service already opened. Nothing here knows OpenSearch exists.

  1. 01 ProductWriteControllerapi POST, PUT and DELETE on /api/v1/products. Binds the request records in WriteRequests and delegates. No logic.
  2. 02 ProductWriteServicewrite The only @Transactional boundary on this path. Loads through the repositories, mutates the entities, then ends every method with the same two lines: product.bumpVersion() and outbox.productChanged(id).
  3. 03 ProductRepository
    VendorRepository
    CategoryRepositoryrepo     Plain Spring Data JPA. The entities they load — Product, ProductVariant, Inventory, Vendor, Category — carry both the write model and the Hibernate Search mapping.
  4. 04 OutboxRecorder
    OutboxStoreoutbox     One narrow INSERT into outbox_event, keyed by aggregate id, no payload. record() is propagation = MANDATORY, so calling it outside a transaction fails loudly instead of quietly reintroducing a dual write.
  5. 05 Hibernate Search listenerlibrary, no code of ours Writes its own rows to hsearch_outbox_event on the same flush — one per touched entity instance, so a product with variants and stock produces several.
Indexing

Two pipelines, drained independently

Both consume an outbox and both end at an alias. They share no code, which is what makes them comparable on identical traffic.

Hand-rolled

outbox · read · projection · indexer
  • OutboxRelay — @Scheduled every 200 ms. Claims a batch with FOR UPDATE … SKIP LOCKED, so every instance can poll without a leader election.
  • ProductAggregateLoader — five batched key lookups turn N ids into N aggregates.
  • ProductProjectionAssembler — pure function, aggregate to ProductDocument. Unit-testable without a cluster.
  • ProductIndexer — one bulk request with external_gte versioning, so a stale or replayed write is a counted no-op rather than a regression.
  • IndexAdmin, ReindexService — versioned indices behind aliases; a rebuild is an alias move.

Hibernate Search

domain · query.hibernatesearch
  • Product — the mapping lives on the entity. @Indexed, @FullTextField, @KeywordField, and the derived @Transient getters for price, stock regions and flattened attributes.
  • @IndexingDependency — declares which persistent properties each derived value reads. This is what reindexes a product when a variant's price changes three tables away.
  • The event processor, the projection step and the bulk write are all library code. There is no relay, assembler or indexer of ours on this lane.
  • HibernateSearchAdmin — the only class we own here: mass index, backlog, aborted events.
Read path

Pick an engine, get ids, hydrate

  1. 01 ProductQueryControllerapi Binds the query string into one ProductQuery record — the engine-independent description of a complex GET. Caps the page size and parses repeated attr=key:value pairs.
  2. 02 ProductReadServiceread Asks for a few more ids than the page needs, hydrates, trims back, and reports how many ids the index named that MySQL no longer had. Widens and retries if the page still came up short.
  3. 03 ProductSearchRouterquery The migration switch: MYSQL, SHADOW, OPENSEARCH or HIBERNATE_SEARCH, overridable per request. Falls back to MySQL on error, and deliberately does not fall back on a deep-paging rejection.
  4. 04 MySqlProductSearchAdapter
    OpenSearchProductSearchAdapter
    HibernateSearchProductAdapterquery.mysql · .opensearch · .hibernatesearch     Three implementations of ProductSearchPort, all returning the same SearchSlice of ordered ids. The OpenSearch one delegates clause building to ProductQueryTranslator.
  5. 05 ProductAggregateLoaderread Hydrates the page by primary key. Cost is proportional to the page, not the result set — twenty ids, five batched queries.
  6. 06 PageResponseapi.dto Carries which engine answered and where the milliseconds went, so a migration is observable from the response itself.
On both paths

The shared spine

ProductAggregateLoader is used twice, on purpose

The indexing pipeline calls it to build the document. The read path calls it to hydrate the page. One loader, two consumers — so the shape of an aggregate is defined in exactly one place, and a projection cannot quietly disagree with a response.

Three more types cross both paths for the same reason: ProductQuery and SearchSlice are what let three adapters be interchangeable, and MinorUnits is the single definition of money-as-an-integer that both the hand-rolled projection and the entity's derived getters call — because a currency amount must never be indexed as a floating-point value.
